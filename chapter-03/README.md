# 第 3 章 编写网络爬虫：学习笔记

第 1、2 章都是「单页」：给一个 URL，取一次，解析一次，任务就结束了。本章把爬虫推成**会走路的**东西 —— 从一页拿到链接，筛选、去重、跳进去，再拿链接，如此往复。核心机制一句话：爬虫 = 「请求 → 解析 → 过滤 → 去重 → 跳转」的循环，循环能转多久、转得多稳，全看过滤和去重这两道工序做得多严。一旦开始「自动跳转」，两个新问题立刻出现：**怎么不让它绕圈子**（去重与上限），以及**怎么不让对面把你封了**（限速与礼仪）。本章的 `wikipedia_crawler.py` 用一个 while 风格的 for 循环把这两件事都演示了一遍，它也是第 4 章「爬虫模型」与第 16 章「并发抓取」的共同前身 —— 后面所有更复杂的爬虫，都是在这个五步循环上加东西。

**本章目标**

1. 编写能在站内**自动跳转**的爬虫（遍历），理解「请求 → 解析 → 过滤 → 去重 → 跳转」五步循环
2. **链接去重**，避免重复抓取与 A→B→A 死循环
3. **筛选有效链接**，用路径前缀 + 名字空间规则 + 正文区域定位三重手段减少菜单、页脚等噪声
4. 写出带异常处理、**可安全停止**的循环/递归思路（上限、判空、失败即停）
5. **礼貌抓取**：延迟、限速、合规 `User-Agent`、遵守 `robots.txt`

---

## 1. 核心知识点与原理

### 1.1 五步循环：把爬虫看成状态机

任何站内爬虫都可以拆成五步：

1. **打开页面**：构造请求、拿到 HTML 字节流
2. **提取链接**：从 DOM 中找出所有 `<a href>`
3. **过滤**出目标链接：路径规则、区域规则、协议规则
4. **去重**：已访问过的不再进队列（`set`）
5. **继续请求**：跳转到下一个 URL，回到第 1 步

第 3、4 步是本章的全部价值所在；第 1、2、5 步第 1 章已经会了。把这五步画成状态机，每个页面的一生是这样的：

```text
[发现] --入队--> [待访问] --取出--> [请求中] --成功--> [解析+提取链接] --过滤/去重--> 产生新的[发现]
                    |                    |
                    |                    --失败--> [重试或放弃]（单页失败不影响全局）
                    |
                    --已在 visited 集合中--> [丢弃]（这里是防死循环的唯一闸门）
```

关键洞察：**去重检查必须发生在「请求之前」而不是「入库之前」**。`wikipedia_crawler.py` 的 `random_crawl` 在循环开头就查 `visited_pages`，命中即停 —— 如果等抓完再查，重复页面的请求流量已经花出去了。

### 1.2 链接过滤：维基名字空间详解

以维基百科为例，有效的**词条**链接要同时满足三个条件：

- 路径以 **`/wiki/`** 开头 —— 排除 `/w/`（API 与脚本入口）、`/static/` 等非内容路径
- **不含冒号** —— 这是排除**名字空间**的关键。维基的 URL 结构是 `/wiki/名字空间:页面名`，普通词条没有名字空间前缀，一旦出现冒号就是功能性页面
- 尽量只在 **`#bodyContent`** 内取 `<a>`，减少侧栏、导航模板、页脚的噪声链接

被冒号规则排除的常见名字空间：

| 名字空间 | 用途 | 为什么要排除 |
|---|---|---|
| `Special:` | 特殊页（搜索、随机页、上传） | 内容是动态生成的，没有抓取价值 |
| `File:` | 文件描述页 | 我们要的是词条正文，不是图片说明 |
| `Help:` / `Wikipedia:` | 帮助与项目文档 | 属于「关于维基」的元信息，不是知识本体 |
| `Talk:` / `User_talk:` | 讨论页 | 内容是编辑讨论，非词条 |
| `Category:` | 分类索引页 | 看需求；做词条图遍历通常排除 |
| `Template:` | 模板页 | 纯排版组件 |

对应的正则表达式：

```python
re.compile(r"^(/wiki/)((?!:).)*$")
```

拆解：`^(/wiki/)` 锚定路径前缀；`((?!:).)*` 中 `(?!:)` 是**否定前瞻**，要求每个字符位置上都不能是冒号，逐字符检查直到路径结尾。它与 `#bodyContent` 的区域限定叠加，构成「区域过滤 + 路径过滤」的双重保险。

### 1.3 去重：为什么是 set

**`set()`** 是标准做法：基于哈希表，插入与成员测试平均 **O(1)**，用它记录已访问过的路径即可。三种常见方案一句话对比：

| 方案 | 成员测试复杂度 | 内存 | 结论 |
|---|---|---|---|
| `list` + `in` | O(n) | 精确存储 | 规模上去后是 O(n²) 的灾难，几千页就明显变慢 |
| `set` | 平均 O(1) | 精确存储 | 本章及绝大多数场景的正确答案 |
| Bloom filter | O(k)，k 为哈希函数个数 | 极省（可压到每元素几 bit） | 亿级 URL 才需要，代价是存在**假阳性**（可能误判已爬而漏抓） |

去重的另一个隐性收益：**它是循环终止的数学保证**。只要站点链接是有限的，且每页都先查重再入队，遍历必然终止；反之不去重的爬虫在任意一个互链环上就会永远转下去。

### 1.4 递归 vs 队列：DFS 与 BFS 各适用什么

| 方式 | 遍历顺序 | 优点 | 代价 | 适用场景 |
|---|---|---|---|---|
| **递归** | 深度优先（DFS） | 代码最短，贴合「顺着链接钻到底」的直觉 | 受递归深度与栈限制，几千层就 `RecursionError`；难断点续爬 | 深度可控的小站点、目录树状结构 |
| **显式栈** | DFS | 不受栈深限制 | 代码稍长 | 需要 DFS 语义但深度不可控时 |
| **显式队列** | 广度优先（BFS） | 按「层」均匀扩展，可断点续爬、可限流、可分布式 | 代码稍长，队列需持久化才能续爬 | 生产爬虫的标准形态，种子站点的全站遍历 |

`wikipedia_crawler.py` 的随机游走是个特例：它**不维护队列**，每页随机挑一个链接跳过去，靠 `MAX_PAGES` 和 `visited_pages` 双重刹车终止。这是演示「跳转 + 去重」的最小骨架；生产环境基本都走显式队列的 BFS —— 第 16 章的多线程抓取也是在这个结构上加并发。BFS 适合「从种子页均匀铺开」（先拿全一级链接再下钻），DFS 适合「尽快到达深层目标页」（比如追分页到最后一页）。

### 1.5 相对 URL 与 urljoin 规范化

HTML 里的 `href` 可能是相对路径（`/wiki/Python`、`../foo`、甚至 `//cdn.example.com/x`），也可能是绝对地址。**去重和请求都必须建立在规范化后的绝对 URL 上**，否则同一个页面的两种写法会被当成两个页面。标准库给出的答案是：

```python
from urllib.parse import urljoin

absolute = urljoin("https://en.wikipedia.org/wiki/Kevin_Bacon", "/wiki/Python")
# -> 'https://en.wikipedia.org/wiki/Python'
```

规范化还要顺手处理三件事：去掉 `#fragment`（同一页面的锚点不产生新内容）、统一协议与主机大小写、决定是否把查询串纳入去重键。`wikipedia_crawler.py` 作为教学示例简化了这一步 —— 它直接存取 `href` 原文，因为（在编写时的）维基词条链接都是规范的 `/wiki/...` 相对路径，天然已规范化。这个假设在 2026 年的实测中已经被打破，详见第 2 节第 5 条与第 3 节实测记录。

### 1.6 爬虫礼仪：robots.txt、UA 政策与限速

礼貌抓取不是道德加分项，而是**让爬虫能持续运行的工程前提**。三条底线：

- **`robots.txt`**：站点根目录下的机器人协议，声明哪些路径允许抓取、以及建议的 `Crawl-delay`。它无法律强制力，但违反它是最常见的封禁理由；详见第 18 章的深入讨论。
- **User-Agent 政策**：维基媒体基金会要求机器人使用**可识别、带联系方式**的 UA（bot 名 / 版本 / URL 或邮箱），匿名或伪装成浏览器的 UA 会被直接 403。这是少数「写了联系方式反而更安全」的场景。
- **限速**：`time.sleep` 控制单线程节奏，配合总请求量预估（见第 4 节的 QPS 算术）。触发 429（Too Many Requests）意味着已经在消耗站点的耐心，正确响应是**退避**（指数级延长间隔），而不是立刻重试。

异常处理也是礼仪的一部分：单页失败不能拖垮整批任务，更不能在异常路径上疯狂重试 —— 那等于把一次故障放大成一次小型 DoS。

## 2. 异常处理与最佳实践（易错点）

1. **不去重 → 来回跳转、资源耗尽**。现象：爬虫日志里同样的 URL 反复出现，运行几小时内存暴涨，抓到的「页面数」虚高。原因：任意两个互链的页面（A 链 B、B 链 A）就构成死循环，不去重的遍历在图论上等价于在环上无限打转。对策：请求前查 `visited` 集合，命中即跳过或终止；`wikipedia_crawler.py` 在每轮循环开头 `if current in visited_pages: break`，同时把已访问路径写入集合，两道动作缺一不可。

2. **不过滤 → 爬进非目标名字空间，队列被噪声撑爆**。现象：队列几分钟内涨到几万条，仔细一看全是 `Special:`、`File:`、登录页、编辑页。原因：一个维基词条正文区有数百个 `<a>`，其中相当比例指向功能性页面；不过滤就把这些噪声全部入队，每页再放大几百倍。对策：像本章示例一样用「正文区域 + 路径正则」双重过滤，宁可少抓也不错抓 —— 漏掉的词条还能通过其他词条的入链补回来，爬进 `Special:` 页面则是纯浪费。

3. **无延迟 → 触发 429 / 封 IP**。现象：开始一切正常，突然连续收到 403/429，换浏览器手动访问也被拦。原因：人类浏览一页要几秒到几十秒，裸跑的循环一秒能发几十个请求，在站点日志里是肉眼可辨的攻击性流量。对策：单线程固定间隔（本章 `sleep_sec=1.5`），收到 429 时指数退避；需要提速时优先考虑「多台低并发」而不是「单台高并发」。

4. **无异常处理 → 一个 404 让整批任务中断**。现象：跑了几千页后一个 traceback 糊脸，前几小时的进度全在内存里随之蒸发。原因：网络是不可靠的 —— `HTTPError`（404/500）、`URLError`（DNS 失败、连接拒绝）、`OSError`（SSL 中断）随时可能发生。对策：像 `_fetch_bytes` 那样把请求包在 `try / except (HTTPError, URLError, OSError)` 里，失败做有限次重试后返回哨兵值（`None`），由上层决定跳过还是终止；同时定期把进度落盘，给崩溃留条后路。

5. **相对/绝对 URL 混用 → 去重失效，过滤规则悄悄落空**。这是最阴的一条：`/wiki/Python` 和 `https://en.wikipedia.org/wiki/Python` 在 `set` 里是**两个不同的字符串**，不去规范化就等于没去重。更糟的是过滤规则本身可能基于「链接是相对路径」的假设 —— **2026-11-02 实测**发现，英文维基现在返回的词条链接已是 `https://en.wikipedia.org/wiki/...` 绝对地址，本章示例的正则 `^(/wiki/)...` 因此一个也匹配不上，脚本抓完起始页就以「无符合条件的词条链接」退出（详见第 3 节）。对策：所有 `href` 先过 `urljoin` 统一成绝对地址再参与过滤与去重；写过滤规则前先打印一小批真实 `href` 样本，确认假设仍成立。

6. **UA 占位符不替换 → 直接被 403**。现象：脚本原样跑就全线 403，而浏览器打开同一页面正常。原因：示例代码里的 `mailto:you@example.com` 是占位符，维基的 UA 政策要求联系方式真实可达，大量用占位符 UA 的请求早已被纳入拦截规则。对策：运行前把 `HEADERS` 里的邮箱换成自己的；这同时也是「出事时站点能联系到你而不是直接封你」的保险。

7. **无上限 → 爬虫永远不会自己停**。现象：本来想「试跑一下」， Ctrl-C 按晚了几百页，日志刷屏、流量超支。原因：随机游走 + 去重只能在「回到已访问页面」时撞停，而维基这样链接极稠密的图上，几百页内撞回旧页的概率很低。对策：任何探索性爬虫先加硬上限（本章 `max_pages=15`），验证行为正确后再放宽；上限不是偷懒，是给「我还没想清楚的部分」兜底。

## 3. 示例代码

主示例：**`chapter-03/wikipedia_crawler.py`** —— 维基百科随机游走，把「过滤 + 去重 + 限速 + 上限」四件事放进一个循环。

```bash
cd chapter-03
pip install -r requirements.txt
python3 wikipedia_crawler.py
```

**运行前必做**：把脚本里 `User-Agent` 的 **`mailto:you@example.com`** 换成你的真实联系方式（见[维基 User-Agent 政策](https://meta.wikimedia.org/wiki/User-Agent_policy)）。不改的话容易被直接 403。本章依赖仅 `beautifulsoup4>=4.12.0`（见同目录 `requirements.txt`），只读代码不跑脚本可以不装。

### 3.1 `HEADERS` 与全局状态

```python
HEADERS = {
    "User-Agent": (
        "Chapter03WikiCrawler/1.0 (educational notes; "
        "https://github.com/REMitchell/python-scraping; mailto:you@example.com)"
    ),
}

visited_pages: set[str] = set()
```

UA 三段式「bot 名/版本 (说明; 项目地址; 联系方式)」是维基政策推荐的标准形态。`visited_pages` 是模块级 `set`，进程生命周期内持续累积 —— 注意这意味着**同一进程里重复调用 `random_crawl` 会继承历史**，想重跑要重启进程或手动清空。

### 3.2 `_fetch_bytes`：带短重试的请求层

```python
for attempt in range(3):
    try:
        req = Request(url, headers=HEADERS)
        with urlopen(req, timeout=20) as resp:
            return resp.read()
    except (HTTPError, URLError, OSError) as e:
        last_err = e
        time.sleep(0.4 * (attempt + 1))
print(f"访问失败: {last_err}")
return None
```

三个设计细节：超时显式设为 20 秒（不设超时的 `urlopen` 可能在坏网络上挂到地老天荒）；重试间隔 `0.4 * (attempt + 1)` 是简易的线性退避，给偶发的 SSL 中断留恢复时间；三次皆败后返回 `None` 而不是抛异常，把「这页不行」的决定权交给上层，同时 `print` 留下最后一次错误原因。

### 3.3 `get_wiki_links`：双重过滤与三种返回值

流程：拼接完整 URL → `_fetch_bytes` → `BeautifulSoup(raw, "html.parser")` 解析 → `find("div", {"id": "bodyContent"})` 定位正文区 → `find_all("a", href=正则)` 过滤出词条链接。注意这个函数的**返回值是三态**的，调用方据此区分三种局面：

| 返回值 | 含义 | 上层（`random_crawl`）的反应 |
|---|---|---|
| `None` | 整页请求失败（网络层三次重试皆败） | 打印「整页请求失败」并结束 |
| `[]`（空列表） | 页面拿到了，但正文区缺失或无任何匹配链接 | 打印「无符合条件的词条链接」并结束 |
| 非空 `Tag` 列表 | 正常 | 进入随机选链环节 |

把「没抓到页面」和「页面里没有链接」区分开是个好习惯：前者是网络问题（值得重试或报警），后者是数据问题（可能是过滤规则失配）。解析阶段只捕获 `AttributeError`（防御 `Tag` 属性缺失），其余异常让 traceback 暴露 —— 教学代码的取舍：明显的编程错误不应被静默吞掉。

### 3.4 `random_crawl`：主循环的四道刹车

```python
for i in range(max_pages):
    if current in visited_pages:
        print(f"已爬过，停止: {current}")
        break
    print(f"[{i + 1}/{max_pages}] 正在爬取: {current}")
    visited_pages.add(current)
    links = get_wiki_links(current)
    ...
    nxt = random.choice(links)
    href = nxt.attrs.get("href")
    ...
    current = href
    time.sleep(sleep_sec)
```

每轮循环按顺序经过四道刹车，任何一道触发都优雅退出：**① 页数上限**（`range(max_pages)`，默认 15）；**② 撞旧页**（`current in visited_pages`，防绕圈）；**③ 取链接失败或无匹配**（对应 3.3 的三态返回）；**④ href 判空**（`nxt.attrs.get("href")` 用 `.get` 而非 `["href"]`，缺属性时拿 `None` 而不是抛 `KeyError`）。顺序上先打印再 `add` 再请求，`visited_pages` 记录的是「已发起爬取的路径」而非「成功抓到链接的路径」—— 失败的页面同样占一个名额，这个语义与 MAX_PAGES 的「最多请求多少次」一致。循环末尾的 `time.sleep(sleep_sec)`（默认 1.5 秒）放在跳转之后，保证任何相邻两次请求至少间隔这么久。

### 3.5 实测记录（2026-11-02）

在 macOS + Python 3.13（`beautifulsoup4` 已装）下**原样运行**仓库脚本，真实输出：

```text
[1/15] 正在爬取: /wiki/Kevin_Bacon
页面中无符合条件的词条链接，结束

完成。共记录 1 个不同词条路径。
```

只爬了起始页就退出。逐函数排查后定位根因（对应第 2 节第 5 条）：页面抓取与 `bodyContent` 定位都正常（该页正文区共 852 个 `<a>`），但英文维基当前返回的词条链接是 `https://en.wikipedia.org/wiki/...` **绝对地址**（抽样前 15 个 href 证实），正则 `^(/wiki/)...` 匹配数为 0。这正好给第 1.5 节的 urljoin 规范化提供了反面教材：**教学示例里「链接都是规范相对路径」的假设会随站点改版失效**。

为验证爬虫逻辑本身没有问题，另做了**对照实验**（不改仓库代码，仅在临时脚本中把匹配逻辑放宽为兼容绝对地址，`random.seed(20261102)`，限速 1.5 秒），跳转行为完全符合预期：

```text
[1/6] /wiki/Kevin_Bacon                      匹配 493 个词条链接
[2/6] /wiki/The_New_York_Times               匹配 1942 个
[3/6] /wiki/Heed_Their_Rising_Voices         匹配 15 个
[4/6] /wiki/List_of_landmark_court_decisions_in_the_United_States  匹配 2479 个
```

各页被冒号规则排除的链接样本也符合名字空间预期：`Wikipedia:Protection_policy`、`File:Kevin_Bacon_The_Best_You_Can-55_(cropped).jpg`、`Special:BookSources/9780195311891`、`Special:EditPage/...` 等。注意词条间链接数量级差异巨大（15 vs 2479），这正是随机游走覆盖面不可控的直观体现。修复思路（作为练习留给读者）：过滤前先把 href 过 `urljoin`，再把正则放宽为接受可选的 `https://en.wikipedia.org` 前缀。

## 4. 学习贴士

- **给爬虫设「刹车」比设「油门」重要**。`MAX_PAGES` 之类的上限不是偷懒，是让你按 Ctrl-C 之前它已经自己停下了。探索阶段每加一个能力（并发、深度、新站点），先把上限调小一个数量级验证行为。
- **限速要算绝对数值**。`sleep(1)` 意味着单线程最多 1 QPS，10 万页就是 28 小时 —— 先算清楚总页数 / 限速 / 可接受时长这笔账再跑，中途发现「要跑一天」比跑完才知道强。
- **维基、GitHub 这类站点对 UA 敏感**，把联系方式写进 UA 是「不被封」的最低成本手段；反过来，伪装浏览器 UA 是最得不偿失的做法 —— 骗得过日志骗不过行为特征，还放弃了被善意对待的机会。
- **先打印样本，再写规则**。过滤正则、选择器写完后，先对一两个页面打印匹配结果的前 20 条人工核对，再放开循环。本章 3.5 节的失配如果这样验证，第一次运行就能发现。
- **把「跳过的」也记下来**。日志只记抓了什么会漏掉一半信息；记录「因为已访问而跳过」「因为名字空间被过滤」的计数，调试去重与过滤时才有据可查（对照实验中每页的匹配数就是这么来的）。

## 练习建议

1. 运行脚本，观察 3.5 节描述的「仅爬 1 页」现象；按第 1.5 节思路，用 `urljoin` + 兼容绝对地址的正则让爬虫重新走起来（在副本上改，不动仓库原文件）。
2. 起始页改为 `/wiki/Python_(programming_language)`，跑三次对比跳转路径，体会随机游走的不可复现性；再用 `random.seed(固定值)` 复现同一条路径。
3. 改为**顺序**取链接（如总是取第一个合法 `href`），对比随机跳转的覆盖面：顺序版容易顺着导航模板在同一主题内打转，随机版更容易跨主题跳变。
4. 将每次访问的 `article_path` **追加写入**本地 `visited_log.txt`，启动时读回集合，实现断点续爬的雏形；注意处理「写一半进程被杀」导致的截断行。
5. 在日志里增加两类计数：「因已访问被跳过」与「因名字空间被过滤」，跑 50 页后打印汇总，验证你对去重与过滤行为的预测。
6. 把主循环从随机游走改成 **BFS**：维护一个 `collections.deque` 队列，每页提取的链接去重后全部入队，对比相同页数上限下两种策略触达的主题广度。
